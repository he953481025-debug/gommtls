go test -v ./mmtls                      # Run all tests (connect to real WeChat servers)

go mod tidy                             # Tidy dependencies

## Architecture

This is a Go implementation of WeChat's MMTLS protocol (version `0xF104`), a proprietary TLS-like protocol for WeChat client-server communication. Module: `github.com/duo/gommtls`, Go 1.18+.

### Two Client Types (Independent)

- **`MMTLSClient`** (`mmtls/mmtls.go`) — Long-link (persistent TCP). Performs 1-RTT ECDHE or 1-RTT PSK handshakes. After handshake, sends periodic Noop keepalives. Generates `session_long` file for later PSK resumption.

- **`MMTLSClientShort`** (`mmtls/mmtls_short.go`) — Short-link (single HTTP POST). Can perform its own 1-RTT ECDHE handshake independently, or use 0-RTT PSK with a pre-existing session. Generates `session_short` file. Does **not** depend on the long-link client.

### Handshake Modes

1. **1-RTT ECDHE** (long-link, no prior session): Full P-256 key exchange → comKey → handshake keys → signature verification → session ticket → server/client finish → app keys
2. **1-RTT PSK** (long-link, has `session_long.tk.tickets[1]`): Resumes with refresh ticket, same flow but PSK-based ClientHello
3. **1-RTT ECDHE** (short-link, no prior session): Same as #1 but over single HTTP request-response; no ClientFinish sent. Generates session for subsequent 0-RTT requests
4. **0-RTT PSK** (short-link, has `session_short.tk.tickets[0]`): No round-trip; early data key from `pskAccess`, entire request in one HTTP packet

| File | Purpose |
|------|---------|

| `mmtls/session.go` | `Session` struct, `Save`/`LoadSession` for disk persistence (binary format) |

| `mmtls/session_ticket.go` | Session ticket parsing (access + refresh tickets) |
| `mmtls/client_finish.go` | ClientFinish message construction |
| `mmtls/server_finish.go` | ServerFinish message parsing and verification |

### Key Derivation Pattern

All key derivation uses **HKDF-Expand only** (no Extract step), with info = `prefix_string ‖ SHA-256_hash_state`:
- `comKey = SHA-256(ECDH_shared_x)` (32 bytes)
- Traffic keys: HKDF-Expand produces 56 bytes (long-link handshake) or 28 bytes (short-link 0-RTT), split into client/server key+nonce pairs
- PSK keys: derived from comKey with labels `"PSK_ACCESS"` and `"PSK_REFRESH"`

### Record Layer

- Header: `type(1B) | version(2B, 0xF104) | length(2B)`
- Types: `0x15`=Abort, `0x16`=Handshake, `0x17`=Data, `0x19`=System
- GCM additional data: `seqNum(8B) | type(1B) | version(2B) | length(2B)`
- Nonce: base nonce XOR'd with sequence number

### Session Files

Two independent session files in repo root, binary format: `u16len(pskAccess) | u16len(pskRefresh) | sessionTicketBytes`

- `session_long` — Long-link sessions. `tickets[1]` (refresh) used for 1-RTT PSK resumption
- `session_short` — Short-link sessions. `tickets[0]` (access) used for 0-RTT requests

### Code Conventions

- Shared crypto primitives live in `crypto.go`; both `MMTLSClient` and `MMTLSClientShort` delegate to these (e.g., `generateKeyPairs()`, `computeEphemeralSecret()`, `computeTrafficKeyN()`, `verifyEcdsaSignature()`). New crypto logic should go there, not duplicated per client.
- The two client types are fully independent — short-link does not import or depend on long-link. Keep this separation.
- Tests hit real WeChat servers (`szlong.weixin.qq.com:8080`, `dns.weixin.qq.com.cn`); there are no mocks. Tests may fail if servers are unreachable.
