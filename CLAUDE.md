## Build & Test Commands

```bash
go build ./cmd                          # Build the demo binary
go run ./cmd                            # Run demo (requires session file for short-link)
go test -v ./mmtls                      # Run all tests (connect to real WeChat servers)
go test -run Test1RTTECDHEHandshake -v ./mmtls  # Run a single test
go test ./...                           # Run all tests across packages
go fmt ./...                            # Format code
go vet ./...                            # Lint
go mod tidy                             # Tidy dependencies
```

**Note:** `Test1RTTPskHandshake` and `Test0RttPskSendData` require a valid `session` file in the repo root (generated by a prior ECDHE handshake). `Test1RTTECDHEHandshake` works without one.

## Architecture

This is a Go implementation of WeChat's MMTLS protocol (version `0xF104`), a proprietary TLS-like protocol for WeChat client-server communication. Module: `github.com/duo/gommtls`, Go 1.18+.

### Two Client Types

- **`MMTLSClient`** (`mmtls/mmtls.go`) — Long-link (persistent TCP). Performs 1-RTT ECDHE or 1-RTT PSK handshakes. After handshake, sends periodic Noop keepalives. Generates a `session` file for later PSK resumption.

- **`MMTLSClientShort`** (`mmtls/mmtls_short.go`) — Short-link (single HTTP POST). Uses 0-RTT PSK with a pre-existing session. Packs ClientHello + encrypted request + abort into one HTTP body; parses response inline. Requires a valid `Session` loaded from disk.

### Handshake Modes

1. **1-RTT ECDHE** (long-link, no prior session): Full P-256 key exchange → comKey → handshake keys → signature verification → session ticket → server/client finish → app keys
2. **1-RTT PSK** (long-link, has `session.tk.tickets[1]`): Resumes with refresh ticket, same flow but PSK-based ClientHello
3. **0-RTT PSK** (short-link, has `session.tk.tickets[0]`): No round-trip; early data key from `pskAccess`, entire request in one HTTP packet

### Key Files

| File | Purpose |
|------|---------|
| `mmtls/record.go` | Record layer: 5-byte header, AES-128-GCM encrypt/decrypt with counter-based nonces |
| `mmtls/session.go` | `Session` struct, `Save`/`LoadSession` for disk persistence (binary format) |
| `mmtls/const.go` | Protocol constants, hardcoded server ECDSA public key |
| `mmtls/client_hello.go` | ClientHello construction for all three modes |
| `mmtls/server_hello.go` | ServerHello parsing |
| `mmtls/signature.go` | ECDSA signature record parsing |
| `mmtls/session_ticket.go` | Session ticket parsing (access + refresh tickets) |
| `mmtls/utility.go` | Length-prefixed read/write helpers, nonce XOR |
| `utils/http_util.go` | HTTP response parsing from raw bytes |
| `cmd/main.go` | Demo: long-link handshake + noop loop, then short-link DNS request |

### Key Derivation Pattern

All key derivation uses **HKDF-Expand only** (no Extract step), with info = `prefix_string ‖ SHA-256_hash_state`:
- `comKey = SHA-256(ECDH_shared_x)` (32 bytes)
- Traffic keys: HKDF-Expand produces 56 bytes (long-link) or 28 bytes (short-link), split into client/server key+nonce pairs
- PSK keys: derived from comKey with labels `"PSK_ACCESS"` and `"PSK_REFRESH"`

### Record Layer

- Header: `type(1B) | version(2B, 0xF104) | length(2B)`
- Types: `0x15`=Abort, `0x16`=Handshake, `0x17`=Data, `0x19`=System
- GCM additional data: `seqNum(8B) | type(1B) | version(2B) | length(2B)`
- Nonce: base nonce XOR'd with sequence number

### Session File Format

Binary file named `session` in repo root: `u16len(pskAccess) | u16len(pskRefresh) | sessionTicketBytes`
- `tickets[0]` (access) → used for 0-RTT short-link
- `tickets[1]` (refresh) → used for 1-RTT PSK long-link resumption
